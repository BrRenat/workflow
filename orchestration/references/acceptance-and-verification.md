# Ticket acceptance criteria and verification

## Ownership

**Ownership routing (Platforms map, example):** Platforms label `Web` → `example-org/web-app`; Platforms label `API` → `example-org/api`. The map is configured per team in the Jev policy `ownership.component_map`. These operator-maintained map hits are sufficient ownership evidence — do not HOLD for repo confirmation when the ticket already has a mapped Platforms label. Labels outside this map still need other evidence.


| Artifact | Answers | Owner | Authority |
| --- | --- | --- | --- |
| Ticket acceptance criteria (AC) | WHAT must work? | Human / ticket owner | Sole source of truth for acceptance |
| Verification Plan | HOW will we prove it works? | Verification Planner, step 04 | Derived checks; cannot change product intent |
| Independent verification result | Does the evidence support each AC? | External reviewer, step 06B | Scoped result for the current issue revision and candidate head |

Jev must never infer or create missing acceptance criteria. Neither the planner nor
the coding/review agent may create, expand, rewrite or "improve" them. Descriptions,
designs, code and existing tests provide context, not substitute acceptance criteria.
If they conflict with the ticket AC, request a human resolution in the tracker.

## Step 02: readiness gate before implementation

WFTasks reads the current ticket through the tracker integration. Check all five conditions:

1. Acceptance criteria are explicitly present. Check presence in code; an empty list
   must fail. No particular heading or AC numbering is required.
2. Their intended outcomes are unambiguous.
3. Each outcome is testable or otherwise verifiable.
4. The criteria do not contradict each other or relevant ticket context.
5. Enough context is available to implement them without inventing product behavior.

Use Jev's typed semantic judgments for conditions 2–5 and the controller's factual
check for condition 1. All must pass; an uncertain answer is not a pass. A missing
or invalid Jev response remains `blocked_jev`, never a fabricated readiness judgment.
Other ownership, risk, dependency, capacity and authorization gates still apply.

Failure means **NOT READY / NEEDS_CLARIFICATION → Human**. Encode this using the
existing `human_attention` disposition and `NEEDS_CLARIFICATION` reason code, with
the failed gate, source reference, exact missing specification and responsible owner.
Keep the current ticket status; do not promote or launch implementation. Do not
draft guessed AC as part of this result. The owner updates the ticket and returns it to WFTasks 01, which
refetches before asking Jev 02 to rerun readiness. Never return directly to Jev. A chat approval without the ticket update does not
fill missing AC.

For a ticket containing only "Fix responsive layout", a suitable result is:

```text
NOT READY — NEEDS_CLARIFICATION
Reason: Acceptance criteria are insufficient to determine expected responsive behavior.
Missing specification:
- expected container-based behavior
- relevant breakpoints / behavior boundaries
- expected resize behavior
Owner: ticket / product owner; update the ticket.
```

List only gaps material to that ticket; do not require irrelevant fields by template.

## Planning inside 04: produce a Verification Plan

The worker retrieves the ticket directly after the minimal Superset handoff. Use the
current AC and issue revision, not an acceptance contract generated by an agent.
If retrieval reveals changed or insufficient AC, stop implementation and return to
the clarification gate. The design integration belongs to workers for linked designs, not WFTasks.

For each existing AC, record its exact source text/reference and:

- verification strategy;
- required test types;
- concrete test scenarios;
- relevant boundary and negative cases;
- expected evidence and the criterion each check proves.

Stable local labels such as `AC-1` may index unnumbered ticket criteria without
rewriting them. Preserve a source reference and issue revision. Each scenario's
expected outcome must follow from existing AC/context; do not invent breakpoints,
business rules or new product obligations. An undefined expected outcome is a
clarification request. Additional test inputs can challenge an existing requirement
without becoming new requirements themselves.

Example, when Jev has established sufficient context in the tracker:

```yaml
source: ticket / current revision / AC-1
acceptance_criterion: Widget layout must depend on its container width rather than browser viewport width.
verification_plan:
  strategy: Vary container and viewport independently; compare behavior with ticket AC.
  test_types: [browser, integration]
  scenarios:
    - narrow container / wide viewport
    - wide container / narrow viewport
    - runtime container resize
    - two widget instances with different container sizes
  boundary_and_negative_cases:
    - vary viewport while container width stays fixed
    - exercise behavior boundaries already specified in the tracker
  expected_evidence:
    - automated Playwright results tied to AC-1 and the candidate head
```

These are ways to prove AC-1, not new AC. This example does not authorize a planner
to decide unspecified responsive behavior. The coding agent implements within the
ticket scope, follows the Verification Plan, and reports actual results and gaps.

## Step 06B: independent verification

The external controller starts a fresh reviewer session. The implementer must not
self-review or launch a reviewer child. The reviewer fetches the ticket directly and
checks both directions: every AC has meaningful checks, and every test assertion
purporting to prove acceptance follows from an existing AC.

**Scope:** Check AC ↔ scenarios ↔ tests ↔ code. Verify that each test would detect a
meaningful violation of its AC.

**Tools:** Independent counterexample search; test-strength analysis; targeted mutation
where useful.

For each criterion, record:

| AC source and revision | Planned scenarios | Tests / actual results | Implementation evidence | Test strength and counterexamples | Verdict / gaps |
| --- | --- | --- | --- | --- | --- |
| AC-1, exact ticket reference | Scenario IDs | Test IDs, assertions, run and head | Relevant code/behavior | Meaningful AC violation each test detects; cases tried, mutation if useful, outcomes and limits | VERIFIED, FAILED or UNVERIFIED |

Challenge the implementation and tests independently of the coding agent's plan:
look for allowed inputs, boundaries, negative cases and interactions that violate
the AC even when existing tests pass. A passing test of the wrong expected behavior
does not verify the AC. Record the search performed and any counterexamples; do not
claim exhaustive correctness from a finite search.

An AC-to-test mapping alone does not establish proof. For the container-width AC,
`expect(component).toBeDefined()` could pass even if layout incorrectly uses viewport
width. Ask: if the implementation violated this AC, would the test fail? Try a targeted
container-to-viewport substitution where useful; record the expected failure mechanism
and actual result if run. A vacuous assertion is a finding, not a VERIFIED criterion.

Mutation testing inside 04 asks whether automated tests detect implementation changes;
06B semantic test-strength review asks whether they detect violations of the actual AC.
Mutation is targeted where useful, not a mandatory blanket test suite. Neither a high
mutation score nor finite reasoning alone proves all behavior.

Mark an AC `VERIFIED` only when its applicable planned checks and implementation
evidence support it, required independent checks were performed, and no unresolved
counterexample or evidence gap remains. Record failures and unverified cases
explicitly. Missing product intent goes to the owner for a ticket update; a known
violation returns as a finding for externally scheduled implementation.

Changed AC require a fresh readiness gate, updated verification mapping and renewed
affected review. Changed code invalidates affected evidence. Verification is scoped
to the recorded revision, head and environment; it does not itself authorize merge
or release. A review pass goes to QA Develop (07); only its current-build pass permits
the staging decision (09). Merge/release gates remain separate.
