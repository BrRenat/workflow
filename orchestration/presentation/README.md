# Workflow presentation

An interactive, single-page presentation and explorer for the approved workflow
([PIPELINE.md](../PIPELINE.md), diagram in [`../assets/workflow.svg`](../assets/workflow.svg)).
It re-draws the approved diagram as interactive SVG from structured data. Every stage, arrow,
decision, connector, rule, skill, artifact and AC trace can be inspected. The committed
diagram files are **not** modified or regenerated by this page.

## Open it

No build step, backend or network access is needed.

- **Locally:** open `orchestration/presentation/index.html` in a browser (works from `file://`).
- **Static hosting:** serve the `orchestration/presentation/` folder as-is, e.g.
  `npx serve orchestration/presentation` or any static host.

Modes: **Explore** (click anything), **Present** (workflow tour, `←` `→` `Esc`) and
**Walkthrough** (the illustrative web widget ticket WEB-123). Deep links such as `#step-06b`,
`#agent-jev`, `#ac-3`, `#skill-counterexample-search`, `#edge-03-04`, `#present-5` and
`#explorer-ci` restore the view. Press `?` for all shortcuts.

The landing page introduces the three tool roles and loops one illustrative ticket,
WEB-123, through a simplified flow: WFTasks, Jev (or a human), WFCoder, Jev, review with
rework, QA, Jev and WFRelease. That sketch is not the approved diagram. The landing fills
the first screen; the explorer starts below it. **Start walkthrough**
enters the existing example; **Explore workflow** opens the unchanged diagram, and
**Set up** leads to installation and the two run modes. Direct links to steps and
walkthroughs skip the introduction. Native anchors `#top`, `#workflow` and
`#setup` also work. Full installation instructions live in [SETUP.md](../../SETUP.md).

## Social preview and publishing

The page includes Open Graph and X summary-card metadata and a 1200 × 630 PNG at
`assets/social-preview.png`. Its editable source is `assets/social-preview.svg`; it is a
separate title card, not a replacement for the approved workflow diagram.

The default image URL points to this repository's public `master` version. It becomes
available after the changes are merged and the repository is public. For a deployed
site, use its own asset URL and canonical page URL instead. From the repository root:

```sh
node orchestration/presentation/scripts/configure-sharing.mjs https://your-host.example/workflow/
```

Replace the example with the actual HTTPS page URL, ending in `/` or `.html`. The script
updates canonical, Open Graph URL and both image URLs in the static HTML so crawlers
can read them without JavaScript. Publish the entire presentation folder, including
`assets/`, and ensure the page and PNG are publicly accessible. The GitHub setup link
targets `master/SETUP.md`, so merge the guide before the public announcement.

Preview the WEB-123 example at `#walkthrough-1`, or go directly to its independent
review findings at `#walkthrough-8`. Label recordings of it as an illustrative example.

## Where things live

| File | Contents | Provenance label in the UI |
| --- | --- | --- |
| `data/workflow.js` | Topology copied from the approved SVG: stages (with verbatim Ready / Scope / Tools / Pass), human boxes, diamonds, connectors, groups, notes, arrows (`edges`), implicit transitions, agents, filters | Approved diagram |
| `data/rules.js` | `rules`: verbatim quotes with `file` + `section`; `skills`: groups of rules per agent; `sourceFiles` embedded for the source viewer | Actual rule |
| `data/content.js` | Per-node details (responsibility, must-not, inputs/outputs…), edge transfers, artifacts, Jev decision points, human touchpoints, CI checks, phases, glossary | Documentation explanation |
| `data/example.js` | Illustrative WEB-123 ticket: AC, Verification Plan, tests, mutation, test strength, counterexamples, AC traces, presentation / walkthrough decks | Illustrative example |
| `data/sources.js` | **Generated** verbatim copies of the rule files for the read-only source viewer | — |
| `js/*.js` | Rendering only: `diagram.js` (SVG, pan/zoom), `panels.js` (drawer, explorers), `evaluators.js` (Explain-decision logic), `app.js` (state, routing, search), `landing.js` (hero flow animation; its steps and captions are in `index.html`) | — |

The UI renders from `window.WFWorkflow`. Adding data does not require UI changes.

## Update explanations without changing the diagram

For responsibility, request preparation, rule or source-viewer corrections, update
`data/content.js` and `data/rules.js`, then regenerate `data/sources.js` and run provenance
tests. Do not change the SVG/PNG or `data/workflow.js` for documentation-only changes.
Step 01 request examples and the builder are in `jev/references/request-preparation.md`
(relative to the repository root).

## Update diagram topology or card text

1. Change the approved diagram first, and only on an explicit request (see
   [AGENTS.md](../../AGENTS.md)). This page must mirror the diagram, never lead it.
2. Mirror the change in `data/workflow.js`. Box coordinates, card lines (keep the diagram's
   wrapping), arrows (`points` are the polyline corners) and label rectangles come from the SVG.
3. Add or update the node's entry in `WF.details` (`data/content.js`), its outgoing
   `WF.edgeDetails`, and its phase in `WF.phases`.
4. Run the tests. `tests/diagram-fidelity.test.mjs` fails if any stage, card line, arrow, label
   or diagram text differs from the SVG, or if diagram text is left unrepresented.

## Attach a rule or skill source

1. Add a rule to `WF.rules` in `data/rules.js`:
   `R(id, agent, title, file, section, quote)`. `section` is the exact Markdown heading text
   (or a dotted JSON key path). `quote` must be copied verbatim; whitespace may differ.
2. Reference the rule id from a skill (`WF.skills[].rules`), a node (`WF.details[id].rules`),
   an edge, an artifact or a Jev decision.
3. If the file is new, add it to `WF.sourceFiles`, then regenerate the embedded copies:
   `node orchestration/presentation/scripts/build-sources.mjs`.
4. `tests/provenance.test.mjs` fails if a quote is not found in that file and section, or if
   `data/sources.js` is stale. Never present invented text as an actual rule; put
   explanations in `content.js`, where they are labelled as documentation.

## Add an example or AC trace

- AC, plan, tests and verdicts live in `WF.example` (`data/example.js`). Keep the example's
  AC written as if by the human ticket owner. Agents never author AC.
- A trace is `WF.example.trace['AC-n']`: an ordered list of `{ node, title, text, edges?, verdict? }`
  using existing node / edge ids. The last `verdict` must match the AC's final round.
- Presentation steps are in `WF.decks` (`{ focus, title, text, edges?, artifact? }`).
- `tests/data-integrity.test.mjs` checks that every reference resolves. It also checks the
  mandatory constraints: only humans produce AC, the planner must-not text, and the minimal
  Superset payload.

## Tests

```sh
cd orchestration/presentation
npm install        # installs Playwright (optional; uses a global install if present)
npm test           # data, provenance, evaluator and browser-interaction tests
npm run test:data  # without a browser
```

The browser tests skip with a message if Playwright is unavailable. Set
`PLAYWRIGHT_CHROMIUM_PATH` to use a specific Chromium binary.

## Boundaries

This page documents the process; it does not enable automation. Both example policies stay in
shadow mode with every action grant disabled, and the Explain-decision views say so. ticket AC
remain the sole source of truth for product acceptance.
